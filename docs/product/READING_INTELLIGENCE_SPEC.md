\# 湛箴面板：閱讀智能體與思路蒸餾規格



> 文件狀態：Draft v0.1  

> 專案：ZhanZhen Panel  

> 定位：本地優先的跨端智能文件工作台  

> 核心能力：讀懂文章的結構、論證、語言與思路，再協助使用者依照可確認的思路寫作  

> 最後更新：2026-09-09



\---



\## 1. 核心問題



一般 AI 寫作工具通常做的是：



```text

輸入一句需求

&#x20;   ↓

AI 直接生成一篇看似流暢的文字

```



但這無法滿足審計、會計、稅務、法律、研究、諮詢、教育、媒體和專業寫作場景。



專業使用者真正需要的是：



```text

既有文章 / 報告 / 文件

&#x20;   ↓

AI 快速閱讀與拆解

&#x20;   ↓

理解「作者如何思考」，而不只記住「作者如何措辭」

&#x20;   ↓

產出可查驗、可修改、可刪除的思路画像

&#x20;   ↓

依照已確認的思路協作完成新的文章或報告

```



本產品的目標不是模仿某個人的表面口吻，而是建立一個可審核的「作者思路模型」。

\## 2. 產品原則



\### 2.1 先理解，後生成



AI 不可在沒有分析或確認作者思路前，直接冒充作者寫正式文章。



正確流程：



```text

讀書 Skill 分析

&#x20;   ↓

使用者檢查思路画像

&#x20;   ↓

女媧 Skill 先生成寫作大綱

&#x20;   ↓

使用者確認或修改大綱

&#x20;   ↓

AI 逐段生成可編輯初稿

&#x20;   ↓

一致性與風險自檢

&#x20;   ↓

使用者匯出

```



\### 2.2 可追溯，不黑箱



每一個閱讀結論都應盡量指向原始來源：



\- Word：章節、段落、表格或註解位置

\- Excel：工作表、儲存格範圍、公式或圖表位置

\- PDF：頁碼、段落、文字區域

\- Markdown / TXT：標題與行號



AI 說「作者先給結論、再給證據」時，介面必須能讓使用者看到相關原文片段。



\### 2.3 使用者擁有資料與判斷權



\- 文件預設在本機保存

\- 使用者可修改、刪除或重建任何思路画像

\- 使用者不同意的分析不得成為後續生成的固定規則

\- 使用者可設定某份文件是否允許雲端 AI 分析

\- 沒有明確同意，系統不把文件傳至第三方 AI 服務



\### 2.4 誠實邊界



AI 可以根據文本提出「寫法觀察」與「可能的溝通功能」，但不可假裝知道作者內心。



系統禁止使用的表述：



```text

作者一定是因為……

作者的真實意圖是……

作者的人格特質是……

作者故意要……

```



系統推薦的表述：



```text

從本文與其他樣本可觀察到……

這種安排可能有助於……

此結論的文本依據是……

跨樣本一致性為高 / 中 / 低……

資料不足，暫不推斷……

```

\## 3. 支援文件類型



\### 3.1 第一階段：正式支持



| 文件類型 | 副檔名 | 讀書分析 | 編輯 | 匯出 | 備註 |

|---|---|---:|---:|---:|---|

| Markdown | `.md` | 是 | 是 | `.md`、`.html` | 最先完成，適合驗證核心流程 |

| 純文字 | `.txt` | 是 | 是 | `.txt`、`.md` | 最低複雜度入口 |

| Word 文件 | `.docx` | 是 | 部分 | `.docx`、`.md`、`.pdf` | 讀取正文、標題、表格、註解與基本格式 |

| Excel 文件 | `.xlsx` | 是 | 部分 | `.xlsx`、`.csv`、`.md` | 讀取工作表、表格、欄位、公式與圖表描述 |

| 文字型 PDF | `.pdf` | 是 | 批註優先 | `.pdf`、`.md` | 需能選取文字，保留頁碼定位 |



\### 3.2 第二階段：逐步完善



| 能力 | 狀態 | 說明 |

|---|---|---|

| Word 高保真排版與修訂追蹤 | 規劃中 | 先保證內容與結構正確，再提高排版還原度 |

| Excel 單元格級公式編輯 | 規劃中 | 第一階段以讀取、解釋、分析和匯出為主 |

| PDF 註解與重組 | 規劃中 | 支援重點、批註、頁面引用與報告導出 |

| OCR 文字辨識 | 敬請期待 | 用於掃描 PDF、圖片、印章遮蓋件、拍照件與手寫件 |

| 本地 OCR | 規劃中 | 優先本地運行，減少客戶資料外傳風險 |



\### 3.3 掃描型 PDF 的處理



系統先偵測 PDF 是否具有可提取文字：



```text

可提取文字

&#x20;   ↓

正常進入 PDF 閱讀與分析流程

```



```text

無可提取文字 / 掃描件

&#x20;   ↓

狀態：OCR\_PENDING

&#x20;   ↓

顯示「OCR 文字辨識：敬請期待」

&#x20;   ↓

不假裝已理解文件內容

```



固定公告文案：



> \*\*OCR 文字辨識：敬請期待\*\*  

> 目前湛箴面板可分析可選取文字的 PDF。掃描件、拍照件、印章覆蓋件與手寫件的本地 OCR 辨識正在開發。OCR 上線前，系統不會聲稱已完整理解掃描型 PDF。

PDF24 是第三方 PDF 工具，不接入 API，不由湛箴面板自動上傳文件。



產品只提供一張外部工具入口卡片，供使用者自行選擇處理 PDF 的合併、拆分、壓縮、轉換與整理需求。



外部網址：



```text

\[https://tools.pdf24.org/zh/](https://tools.pdf24.org/zh/)

```



\### 4.2 右上角卡片文案



```text

可使用 PDF24 Tools。



開啟 PDF24 Tools ↗
```

\- 在外部連結旁標記「第三方」

\- 在開源致謝中註明 PDF24 僅作為使用者自主選擇的外部工具入口

\## 5. 讀書 Skill



\### 5.1 任務



讀書 Skill 不以「摘要」為終點，而是分析：



1\. 這篇文件在解決什麼問題

2\. 作者如何安排全文與章節

3\. 每個段落在論證中扮演什麼功能

4\. 作者如何使用資料、準則、案例或其他證據

5\. 作者如何從證據推到判斷和結論

6\. 作者如何處理不確定性、風險與反方觀點

7\. 作者如何使用語言、術語、句型、數字與格式

8\. 哪些發現有充分文本依據，哪些只是低信心推測



\### 5.2 SQ3R 在產品中的映射



| SQ3R 步驟 | 系統能力 | 面板產物 |

|---|---|---|

| Survey 瀏覽 | 掃描標題、層級、表格、圖表、首尾段 | 文章地圖、閱讀概覽 |

| Question 提問 | 將標題、主張與段落改寫成待回答問題 | 問題清單、研究問題卡 |

| Read 精讀 | 提取主張、證據、數據、概念與結論 | 重要片段、重點卡、術語表 |

| Recite 複述 | 用使用者可理解的語言重建論證 | 白話解釋、段落功能說明 |

| Review 複習 | 把高價值規律固化進画像並供用戶修正 | 思路画像、複習卡、變更紀錄 |



\### 5.3 康奈爾筆記在產品中的映射



| 區域 | 系統產物 |

|---|---|

| 左側關鍵字 / 問題區 | 概念、關鍵詞、作者要回答的問題、可複習問題 |

| 主筆記區 | 證據、數據、原文重點、段落作用、論證節點 |

| 底部摘要區 | 本節或全文的濃縮結論與下一步行動 |



\### 5.4 費曼檢驗在產品中的映射



每個「作者思路」結論都要有一份簡明解釋：



```text

專業分析：

作者先引用準則，再列出數據，最後給出審計結論。



白話解釋：

作者不是先憑感覺說有風險，而是先找規則當標準，

再用數據證明情況符合風險條件，所以結論更站得住。

```



若無法用清楚、簡單的語言解釋，系統需標記：



```text

理解不足：需要更多樣本或使用者補充。

```

\## 6. 三類核心流程圖



流程圖不是裝飾，是閱讀智能體最重要、最可驗收的輸出。



所有圖都必須：



\- 可以點擊節點查看來源片段

\- 支援展開、收合、縮放與匯出

\- 支援使用者修改節點文字、連線與分類

\- 支援匯出 Mermaid、PNG、SVG、JSON

\- 為每個節點保存來源定位與分析可信度



\### 6.1 文章結構圖



問題：



> 這篇文章是如何被搭建起來的？



節點類型：



```text

標題

背景

問題

定義

主張

子論點

證據

案例

反方觀點

風險

結論

建議

附錄

```



範例：



```mermaid

flowchart TD

&#x20; A\[文章標題] --> B\[背景：應收帳款逾期上升]

&#x20; B --> C\[問題：回款風險是否增加]

&#x20; C --> D\[主張：需提高減值評估關注度]

&#x20; D --> E\[數據分析]

&#x20; D --> F\[準則依據]

&#x20; E --> G\[風險結論]

&#x20; F --> G

&#x20; G --> H\[整改建議]

```



\### 6.2 論證與證據流程圖



問題：



> 作者如何從事實與證據，推導出一個結論？



節點類型：



```text

觀察 / 事實

問題

假設

準則 / 判斷標準

證據

數據檢驗

推理

限制條件

風險

結論

建議

```



每條連線要有關係類型：



```text

支持

反駁

導致

例證

限制

推導

對比

補充

```



範例：



```mermaid

flowchart TD

&#x20; A\[事實：逾期比例增加] --> B\[問題：是否存在回款風險]

&#x20; B --> C\[標準：減值評估相關準則]

&#x20; C --> D\[取得賬齡分析表]

&#x20; C --> E\[核對歷史回款紀錄]

&#x20; D --> F\[推理：可收回性降低]

&#x20; E --> F

&#x20; F --> G\[結論：減值準備可能不足]

&#x20; G --> H\[建議：追加審計程序]

```



\### 6.3 作者思路图



問題：



> 這位作者或這個團隊遇到一個專業問題時，通常如何思考、判斷與寫作？



節點類型：



```text

任務輸入

問題界定

判斷標準

優先證據

分析方法

結論策略

不確定性處理

風險披露

建議輸出

語言表達

```



範例：



```mermaid

flowchart TD

&#x20; A\[收到審計問題] --> B\[先界定範圍與判斷口徑]

&#x20; B --> C\[引用準則與制度要求]

&#x20; C --> D\[核對原始憑證與財務數據]

&#x20; D --> E\[交叉驗證例外情況]

&#x20; E --> F\[先給明確結論]

&#x20; F --> G\[單列不確定事項與影響]

&#x20; G --> H\[提出可執行整改建議]

```



\### 6.4 圖形輸出要求



每份分析至少產生：



```text

1 張文章結構圖

1 張論證與證據流程圖

1 張作者思路圖

```



如果證據不足，圖可以只展示已知節點，但必須標示：



```text

待確認

證據不足

使用者補充

低信心推測

```

\## 7. 思路画像（Writing DNA）



\### 7.1 画像不是單純文風



思路画像應至少覆蓋五層：



| 層次 | 內容 |

|---|---|

| 認知框架 | 作者如何界定問題、拆解問題與安排整體結構 |

| 決策啟發式 | 作者判斷輕重緩急、選擇證據與形成結論的規律 |

| 表達 DNA | 語氣、句式、術語、轉場、數字與格式習慣 |

| 價值與反模式 | 重視什麼、避免什麼、哪些表達方式不採用 |

| 誠實邊界 | 證據不足時如何說明、不應推斷什麼、適用範圍在哪裡 |



\### 7.2 必須可見與可修改



使用者應能在「思路画像」頁面：



\- 查看每項規律

\- 查看其原文證據

\- 編輯文字

\- 調整優先級

\- 標為「確認」「待觀察」「不準確」「刪除」

\- 指定只適用於某個文件類型，例如審計報告、稅務說明、商業研究或英文郵件

\- 按個人、團隊、事務所或客戶專案建立不同画像

\- 隨時刪除画像與其索引資料



\### 7.3 可信度規則



| 級別 | 條件 | 系統行為 |

|---|---|---|

| 高 | 至少三份樣本反覆出現，且有清晰原文依據 | 可作為預設寫作規則 |

| 中 | 兩份樣本出現，或一份樣本中多次出現 | 建議用戶確認後使用 |

| 低 | 單一片段推測，或證據含糊 | 僅顯示為觀察，不作固定規則 |

| 未確認 | AI 已分析但使用者未確認 | 不得用於正式生成 |

| 已否決 | 使用者標記不準確 | 不得再次當作推薦規則 |

\## 8. 女媧 Skill



\### 8.1 任務



女媧 Skill 使用「已確認的思路画像」和「可追溯的參考片段」，協助使用者完成新寫作任務。



它不應直接一鍵生成整篇正式文件，而應遵守：



```text

任務理解

&#x20;   ↓

檢索相關画像與歷史片段

&#x20;   ↓

生成思路大綱

&#x20;   ↓

使用者確認

&#x20;   ↓

逐段生成

&#x20;   ↓

使用者編輯

&#x20;   ↓

一致性與風險檢查

&#x20;   ↓

匯出

```



\### 8.2 大綱先行



女媧 Skill 第一次輸出必須是「思路大綱」，至少包括：



\- 標題候選

\- 受眾與目的理解

\- 文章/報告章節

\- 每個章節要回答的問題

\- 每個章節的核心主張

\- 需要的數據、證據或待補充資料

\- 要遵守的作者思路規律

\- 尚未確認的假設與風險



使用者點擊「確認大綱」前，女媧 Skill 不得直接產出完整正式報告。



\### 8.3 分段創作



每次只生成一個段落或小節，並提供：



```text

接受

插入到文件

重寫

縮短

展開

改為更保守

改為更正式

顯示參考來源

標記為待人工補充

```



\### 8.4 自檢



在生成完成後，系統應檢查：



\- 是否遵守已確認的章節邏輯

\- 是否使用了應使用的術語

\- 是否違反禁用詞或表達偏好

\- 是否存在無來源的關鍵結論

\- 是否把低信心分析寫成確定事實

\- 數字、日期、單位與格式是否一致

\- 是否遺漏風險披露或限制條件

\- 是否需要人工專業複核



自檢結果只提供建議，不能替代會計師、審計師、稅務師、律師或其他專業人士的簽字、判斷和法定責任。

\## 9. 智能體狀態機



每個文件分析或寫作任務都應有明確狀態：



```text

DRAFT

&#x20; ↓ 使用者選擇或匯入文件

IMPORTED

&#x20; ↓ 文件類型與內容可正常解析

PARSED

&#x20; ↓ 讀書 Skill 提取結構、證據、語言與思路

ANALYZED

&#x20; ↓ 流程圖和画像已生成，等待使用者審核

AWAITING\_PROFILE\_REVIEW

&#x20; ↓ 使用者確認画像

PROFILE\_CONFIRMED

&#x20; ↓ 女媧 Skill 生成寫作大綱

OUTLINE\_READY

&#x20; ↓ 使用者確認或修改大綱

OUTLINE\_CONFIRMED

&#x20; ↓ 分段生成與使用者編輯

WRITING

&#x20; ↓ 一致性、證據與風險檢查

QUALITY\_REVIEW

&#x20; ↓ 使用者輸出文件

EXPORTED

```



PDF 的特殊狀態：



```text

OCR\_PENDING

```



進入 `OCR\_PENDING` 後：



\- 顯示 OCR 敬請期待公告

\- 允許保留 PDF、閱讀頁面與添加人工筆記

\- 禁止聲稱已抽取全文或已理解內容

\- 可由使用者手動貼入文字後再進行分析

\## 10. 使用者確認節點



| 節點 | 是否必須確認 | 原因 |

|---|---:|---|

| 雲端 AI 處理敏感文件 | 是 | 需要資料使用知情同意 |

| 建立或更新思路画像 | 是 | AI 分析可能有偏差 |

| 用画像生成正式任務大綱 | 是 | 防止思路錯誤擴大 |

| 大綱進入逐段寫作 | 是 | 專業文件結構需人工把關 |

| 輸出正式文件 | 是 | 人工承擔最終專業責任 |

| 發送、提交或對外發布 | 是 | 不由 AI 自動執行 |

\## 11. 工作台介面需求



\### 11.1 三欄桌面佈局



```text

左側：導航與文件樹

中間：文件工作區 / 流程圖工作區 / 寫作工作區

右側：湛箴 AI 助手與任務進度

```



\### 11.2 左側導航



```text

首頁

我的文件

讀書分析

流程圖
```

\## 14. MVP 驗收標準



第一個可對外演示的 MVP 必須完成下列閉環：



1\. 使用者在網頁端匯入 3–5 篇脫敏 `.md` 或 `.txt` 文章

2\. 系統在本機保存文件清單與內容

3\. 讀書 Skill 產出文章概覽、重點、問題清單與術語表

4\. 系統產出文章結構圖、論證與證據流程圖、作者思路圖

5\. 每個重要節點可查看來源文字

6\. 系統建立一份可編輯、可確認的思路画像

7\. 使用者新建寫作任務

8\. 女媧 Skill 依照画像先生成大綱

9\. 使用者確認大綱後，AI 支援逐段生成

10\. 生成結果可在頁面編輯並本地保存

11\. 瀏覽器重新整理後，文件、画像、大綱和草稿仍可恢復

12\. Word、Excel、PDF 的按鈕與能力狀態清晰可見

13\. 掃描型 PDF 顯示「OCR 敬請期待」，不假裝可分析

14\. 頂部有 PDF24 外部工具入口與第三方資料安全提示

15\. 所有測試文件都是脫敏或虛構資料

\## 15. 非目標



第一階段不做：



\- 不承諾替代會計師、審計師、稅務師、律師的專業判斷

\- 不自動簽發或提交審計、稅務、法律或財務文件

\- 不自動將文件上傳至第三方工具

\- 不以無法驗證的方式推斷作者心理、人格或真實意圖

\- 不承諾 OCR 已可用

\- 不追求 Word / Excel / PDF 的百分之百格式還原

\- 不先做 Windows EXE、Android APK、雲端多人協作與複雜後端

\- 不為了展示而生成沒有來源依據的結論

\## 17. 最終判斷標準



如果使用者上傳多篇自己的文章後，系統只能說：



```text

你的文章很正式、常用專業術語、句子較長。

```



那系統是失敗的。



如果系統能夠讓使用者看到並確認：



```text

你通常先用什麼方式界定問題；

你選擇哪些證據；

你如何從證據走到結論；

你在哪裡保留不確定性；

你如何披露風險；

你如何把結論轉化為可執行建議；

你怎麼安排一篇文章的結構；

你的寫作規則有哪些可追溯的原文依據。

```



並能依照這些已確認規律，先生成正確思路的大綱、再協作寫出可編輯初稿，才算成功。
